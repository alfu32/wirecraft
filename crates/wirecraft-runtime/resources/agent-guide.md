# Wirecraft agent guide

Wirecraft migrates the Threadworks topology IDE. Libraries define reusable capabilities; processing nodes employ them and route a principal result or coherent typed error; Type entities define boundary values; links expose data, error, dependency and recovery topology. These are design defaults, not prohibitions.

Read threadwork.get_design or a bounded fragment before edits. Use stable IDs and repository tools. Validate after structural changes. Mutations synchronize parents, children, ports and link indexes. Technology and file-layout values normally inherit from the parent. Update source, initialization, specification, tests and aiInstructions through update_entity.text. Partial text/layout/technology/link objects merge; metadata and arrays replace. Root cannot be deleted or reparented; data links cannot point to links. Mutations are atomic and undoable.

The MCP names and resource URIs retain threadwork for client compatibility. The backend and desktop share these services. Inspect list_technologies and command catalog: unavailable graph compilers and UI-only commands are not claimed. Changes remain in memory until an explicit file.save through the application API or supported execute_command, with a path already selected. Headless hosts may opt into recovery snapshots. C/C++ intelligence uses a supervised external clangd and build tools; TCC is absent.

## Wirecraft workflow extensions

Use wirecraft.open_project and wirecraft.save_project for explicit persistence, wirecraft.copy_entities/paste_entities for ID-safe fragments, list/import/save_archetype for reusable .orch workflows, analyze_network for typed graph reports, export_diagram for free-size SVG/PNG/PDF, and component_fiches for Markdown dossiers. Use wirecraft.workbench for real ISO/roll/poster plan and documentation previews/exports, settings, MCP controls, clipboard prompts and explicit printer jobs. Multipage images require PDF; previews never print. Generated output directories must be new or empty; no generation merges into a nonempty directory.

wirecraft.compile_c17 generates one C17 unit from c-native / single-file processing graphs. Source contains recurring statements, Initialization contains setup, service libraries contain translation-unit declarations, and Type entities define boundary structs. A data/error link supplies buffer arguments named from its link name. Use push(buffer, &item), pop(buffer, &item), and threadwork_buffer_count(buffer). Self-feedback uses <link>_in and <link>_out. A dependency (lib) link lends its library's single shared instance to the consumer as an argument named after the link: a link `math` from `lib_math` gives `const Lib_mathLibrary *math`, called as `math->function(...)`; libraries are emitted after the libraries they depend on. Former `link__function` aliases are generated only for bodies that still use them. Model shutdown explicitly with threadwork_runner__shutdown_request(&threadwork_runner); the generated runner drains residual traffic. Source capabilities materialize their provider's declaration through `<link>->getSource(<link>, parameters, count)`. Model-defined template overrides, parameterized collection types and cross-technology aggregation are not complete. C runnable capabilities remain rejected as in the source application; do not assume a runtime compiler exists.

Pluggable components (docs/design/components.md): a design publishes ports by linking entities to Exterior nodes, one link each. Create them with wirecraft.components operation `publish` ({nodeId, direction 'output'|'input', name, typeDefinitionId or typeName plus payloadDefinition}); the Exterior is named <link>Out or <link>In and must not be renamed directly. Such a design is a component and generates only through a design that references it. `reference` ({path inside the saved design's directory}) places a Reference pinned by SHA-256 that lists the published ports; `update_reference` re-pins it after the component changes. Link to a Reference port by setting sourcePortName (outputs, exactly one link each) or targetPortName (inputs, any number of links) to the port name. Consumer links may use a component type as typeDefinitionId `<referenceId>::<typeId>` with typeName for display. compile_c17 expands References; template compilers reject them. One Reference per component per program.

wirecraft.analyze_c17 runs a separate supervised clangd against the generated unit and maps diagnostics to entity text sections and 1-based source locations. Unmapped generated/runtime lines retain their generated location. wirecraft.language_server provides generic LSP lifecycle and document/workspace operations; positions follow the negotiated encoding and versions must increase. wirecraft.build runs executable/args/cwd jobs with bounded output, cancellation and timeout. Project Management uses the six source statuses; null is backlog. Master revision is a document field; node revisions change when nodes are touched, and can inherit from ancestors. Keep editor diagnostics separate from authoritative native compiler/build results. Compile C with an external clang/C17 toolchain, never TCC. Consult advertised capabilities and errors rather than inventing a successful compiler or UI command.

C17 editor context is exposed by wirecraft.workbench operations editor_context, complete and stop_editor. Complete accepts nodeId, section (source or initialization), full uncommitted text and a UTF-8 byte offset. Returned textEdit ranges use Unicode-scalar columns (positionEncoding utf-32); the adapter converts negotiated server positions. It includes actual runtime/types and connected node buffers/library instances, never commits the draft, rejects stale revisions and excludes edits outside the authored body. Vector documentation embeds shared SVG paths/text; preview PNGs are separate.
